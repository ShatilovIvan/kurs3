# Studies 2026 — правила для агента

Лабораторные работы по предметам (группа ФИТ-242, ОмГТУ). Карта папок и сокращений — [README.md](README.md).

## Старт сессии (особенно после /clear)

1. Прочитать `README.md` — какие папки есть.
2. Если пользователь назвал предмет — прочитать `<Предмет>/progress.md` целиком и последние 5 записей `<Предмет>/log.md`.
3. Продолжать с блока «Следующий шаг» в `progress.md`. Не переспрашивать то, что уже записано.
4. Нужны материалы — `<Предмет>/materials/INDEX.md`, не оригиналы (см. «Материалы»).

## Файлы учёта в каждой папке предмета

| Файл | Что | Как менять |
|---|---|---|
| `task.md` | задания, варианты, критерии, ссылки | дополнять, когда появляются новые задания |
| `progress.md` | таблица ЛР + текущий фокус + следующий шаг + открытые вопросы | **перезаписывать** блоки, держать актуальным |
| `log.md` | хронология действий | **только дописывать** вниз, старое не править |

## Правило записи (обязательно)

После каждого значимого действия по предмету — **до** ответа пользователю:

1. Дописать запись в `<Предмет>/log.md`.
2. Обновить `<Предмет>/progress.md`: статус ЛР в таблице, «Текущий фокус», «Следующий шаг», «Открытые вопросы».

Значимое действие: создан/изменён файл решения, запущен код с результатом, принято решение (вариант, подход, стек), получен ответ пользователя на вопрос, найдена/исправлена ошибка, скачаны материалы, ЛР сдана/защищена/получены баллы.

Не значимое: чтение файлов, ответ на вопрос без изменений.

Действие затронуло несколько предметов — писать в каждый. Действие по репозиторию в целом (структура, правила, скиллы) — в корневой [log.md](log.md).

### Формат записи в log.md

```markdown
## 2026-09-27 14:30 — ЛР 1: загрузка данных
- Сделано: <что, какие файлы (относительные пути)>
- Результат: <цифры, вывод, ошибка — дословно, коротко>
- Решения: <что выбрали и почему> (если были)
- Дальше: <следующий шаг>
```

Время брать из системы: Bash `date '+%Y-%m-%d %H:%M'` (не cmd/PowerShell `date`). Запись самодостаточна: читается без контекста чата.

### Статусы ЛР в progress.md

`—` не начата · `в работе` · `готова` (решение есть, не сдана) · `сдана` · `защищена` · `заблокирована` (указать чем)

### Проверка перед ответом

Если в этом ходе менялись файлы в `<Предмет>/solution/` или `task.md`, а `log.md` не тронут — запись забыта, дописать.

## Цикл ЛР

1. **Карта** — «Карта ЛР N» в `progress.md` по материалам (см. «Материалы», правило 2).
2. **`/check-lab <Предмет> N plan`** — скептик атакует карту. Вердикт `начинать` → дальше; иначе поправить карту / задать вопросы пользователю.
3. **Решение** в `solution/labN/`, коммит на каждый значимый шаг.
4. **`/check-lab <Предмет> N solution`** — скептик проверяет решение: критерии, запуск, соответствие курсу, оформление, вопросы защиты. Без вердикта `сдавать` статус `готова` не ставить.
5. Сдача → `сдана` → merge `dev` в `main` (см. «Git»).

Упала ошибка — `/debug`. Проверка — отдельным агентом со свежим контекстом (`.claude/agents/lab-skeptic.md`), не самопроверкой.

## Материалы

Материалы = то, по чему проверяют. Решение, верное «вообще», но не по методичке, не сдаётся.

### Где что лежит

```
<Предмет>/materials/
├── INDEX.md    # оглавление: файлы, сроки, критерии, карта по ЛР, страницы пособий — читать ПЕРВЫМ
├── notes/      # полный текст каждого PDF/DOCX (маркеры <!-- стр. N -->) — искать Grep, не читать целиком
└── ...         # оригиналы
```

### Правила

1. **Порядок доверия:** задание ЛР (`task.md`, методичка ЛР) → методика рейтингового контроля → шаблон → пример → лекции/ноутбуки с пар → пособие → общие знания. Противоречие между источниками — не выбирать самому, спросить пользователя.
2. **Карта перед стартом ЛР.** Перед первой строкой решения: прочитать `materials/INDEX.md`, по нему — нужные куски `notes/`. Записать в `progress.md` блок «Карта ЛР N»: файлы + страницы, требования, критерии. Дальше работать по карте, методички заново не перечитывать.
3. **Читать выжимки, не оригиналы.** Текст искать в `notes/` через Grep по ключевым словам / номеру страницы. Оригинал (PDF/DOCX) открывать только ради картинок, схем, таблиц, потерянных при извлечении.
4. **Критерии → чек-лист.** Требования методички и критерии приёмки переносить чекбоксами в «Карту ЛР N». Статус `готова` — только когда отмечены все.
5. **Методы как на парах.** Библиотеки, подходы, термины — из лекций и ноутбуков преподавателя (раздел в `INDEX.md`). Выход за курс — только с пометкой в решении и причиной в `log.md`: на защите спросят.
6. **Оформление по шаблону.** Титульный лист своей группы (ФИТ), структура отчёта — по шаблону/примеру. Из примеров брать структуру и объём, текст не копировать.
7. **Ссылка на источник.** В решении/отчёте у требования или метода — откуда он: «пособие PostgreSQL, с. 61», «Лекция 2, слайд 12».
8. **Не выдумывать.** Нет в материалах (задания ЛР, варианта, срока) — так и сказать, вписать в «Открытые вопросы» `progress.md`. Не достраивать задание по аналогии.
9. **Архив — не задание.** `materials/archive_*` — только справка.
10. **Новый материал — сразу в учёт.** Положили файл → извлечь текст в `notes/` → строка в `INDEX.md` (+ сроки/критерии, если есть) → запись в `log.md` → коммит `docs(<scope>): add <что>`.

Извлечение текста: PDF — `pypdf` (по странице, маркер `<!-- стр. N -->`), DOCX — `word/document.xml` из zip, DOC — `antiword -m UTF-8.txt`.

## Git

Репозиторий: https://github.com/mm-shkurin/studies_2026 (публичный). Методология — упрощённый GitHub Flow из absolute555/textery: без PR, коммиты прямо в рабочую ветку.

### Ветки

| Ветка | Роль |
|---|---|
| `main` | Стабильное состояние: сданные ЛР, чистая структура. Прямых коммитов нет — только fast-forward из `dev`. |
| `dev` | Рабочая ветка. Все коммиты сюда. |

- Сдали ЛР (статус `сдана` в `progress.md`) → `git checkout main && git merge --ff-only dev && git push && git checkout dev`.
- Отдельные ветки на ЛР не заводить: работа одна, ветка одна.

### 1 запись в журнал = 1 коммит

Значимое действие (см. «Правило записи») завершается **одним коммитом**, в котором лежат вместе:
- изменения работы (решение, задание, материалы);
- новая запись в `log.md`;
- обновлённый `progress.md`.

Порядок: сделать работу → записать `log.md` + `progress.md` → `git add` конкретных путей → коммит → push в `dev` → ответ пользователю.

Мелочи без записи в журнал (опечатка, форматирование) — отдельный коммит `style:`/`docs:` без записи в `log.md`.

### Сообщение коммита

Conventional Commits, английский, повелительное наклонение, до ~72 символов, без точки:

```
<type>(<scope>): <what>

<why — если неочевидно>
```

- `scope` — папка предмета в нижнем регистре (`progpractice`, `webdev`, `se`, `dbms`, `diffeq`, `mathsec`, `nlp`, `ooad`) или `repo` для общего.
- `type`: `feat` — решение/часть ЛР; `fix` — исправление решения; `docs` — задания, материалы, README, журнал без работы; `chore` — структура, конфиги, скиллы; `refactor`, `test`, `style` — как обычно.
- Subject повторяет заголовок записи в `log.md` (по-английски): `feat(progpractice): lab 1 load data and split train/test`.

### Запрещено без явной просьбы

- `git reset --hard`, `git checkout -- .`, `git restore .`, `git clean -fd`, `git push --force` — сначала `git status --short`, закоммитить или спросить.
- `git add -A` / `git add .` вслепую — смотреть `git status`, добавлять пути.
- Коммитить `.claude/settings.local.json`, `.venv/`, секреты, токены.

## Структура предмета

```
<Предмет>/
├── task.md       # задания
├── progress.md   # прогресс и следующий шаг
├── log.md        # журнал действий
├── materials/    # методички, датасеты, шаблоны + INDEX.md + notes/
└── solution/     # решения (по папке на ЛР: solution/lab1/ ...)
```

## Прочее

- Язык общения и документов — русский. Код, коммиты, имена новых файлов решений — латиница.
- Студент должен уметь объяснить каждое действие на защите: решения фиксировать в `log.md` с причиной.
- Персональные данные одногруппников (рейтинги, ФИО) в репозиторий не сохранять — только ссылки.
