# Studies 2026 — правила для агента

Лабораторные работы по предметам (группа ФИТ-242, ОмГТУ). Карта папок и сокращений — [README.md](README.md).

## Старт сессии (особенно после /clear)

1. Прочитать `README.md` — какие папки есть, «Панель» (сроки и следующий шаг по всем предметам).
2. Если пользователь назвал предмет — прочитать `<Предмет>/progress.md` целиком и последние 5 записей `<Предмет>/log.md`.
3. Продолжать с блока «Следующий шаг» в `progress.md`. Не переспрашивать то, что уже записано.
4. Нужны материалы — `<Предмет>/materials/INDEX.md`, не оригиналы (см. «Материалы»).

## Файлы учёта в каждой папке предмета

| Файл | Что | Как менять |
|---|---|---|
| `task.md` | задания, варианты, критерии, ссылки | дополнять, когда появляются новые задания |
| `progress.md` | таблица ЛР + текущий фокус + следующий шаг + открытые вопросы | **перезаписывать** блоки, держать актуальным |
| `log.md` | хронология действий | **только дописывать** вниз, старое не править |

## Правило записи (обязательно)

После каждого значимого действия по предмету — **до** ответа пользователю:

1. Дописать запись в `<Предмет>/log.md`.
2. Обновить `<Предмет>/progress.md`: статус ЛР в таблице, «Текущий фокус», «Следующий шаг», «Открытые вопросы». Изменился «Следующий шаг» или срок — поправить строку предмета в «Панели» `README.md`.

Значимое действие: создан/изменён файл решения, запущен код с результатом, принято решение (вариант, подход, стек), получен ответ пользователя на вопрос, найдена/исправлена ошибка, скачаны материалы, ЛР сдана/защищена/получены баллы.

Не значимое: чтение файлов, ответ на вопрос без изменений.

Действие затронуло несколько предметов — писать в каждый. Действие по репозиторию в целом (структура, правила, скиллы) — в корневой [log.md](log.md).

### Формат записи в log.md

```markdown
## 2026-09-27 14:30 — ЛР 1: загрузка данных
- Сделано: <что, какие файлы (относительные пути)>
- Результат: <цифры, вывод, ошибка — дословно, коротко>
- Решения: <что выбрали и почему> (если были)
- Дальше: <следующий шаг>
```

Время брать из системы: Bash `date '+%Y-%m-%d %H:%M'` (не cmd/PowerShell `date`). Запись самодостаточна: читается без контекста чата.

### Статусы ЛР в progress.md

`—` не начата · `в работе` · `готова` (решение есть, не сдана) · `сдана` · `защищена` · `заблокирована` (указать чем)

### Проверка перед ответом

Если в этом ходе менялись файлы в `<Предмет>/solution/` или `task.md`, а `log.md` не тронут — запись забыта, дописать. Страховка — Stop-хук `.claude/hooks/check-log.sh`: при таких незакоммиченных изменениях без правки `log.md` он не даёт закончить ход.

## Цикл ЛР

1. **Карта** — `/start-lab <Предмет> N`: «Карта ЛР N» в `progress.md` по материалам (см. «Материалы», правило 2, и шаблон ниже).
2. **`/check-lab <Предмет> N plan`** — скептик атакует карту. Вердикт `начинать` → дальше; иначе поправить карту / задать вопросы пользователю.
3. **Решение** в `solution/labN/`, коммит на каждый значимый шаг.
4. **Ручные шаги** (если есть в Карте) — агент готовит черновик и инструкцию, студент делает в GUI-инструменте и кладёт скриншоты в `solution/labN/img/`. Пока не сделаны — статус `в работе`, «Следующий шаг» = «Студент: <что сделать руками>».
5. **Отчёт** (если ЛР сдаётся документом) — `solution/labN/report.docx` по шаблону/примеру, титул группы ФИТ-242 (см. «Отчёт»).
6. **`/check-lab <Предмет> N solution`** — скептик проверяет решение: критерии, запуск, соответствие курсу, оформление, отчёт, вопросы защиты. Без вердикта `сдавать` статус `готова` не ставить.
7. Сдача → `сдана` → тег сдачи (см. «Git»).
8. Перед защитой — `/defense <Предмет> N`: тренировка ответов.

Упала ошибка — `/debug`. Проверка — отдельным агентом со свежим контекстом (`.claude/agents/lab-skeptic.md`), не самопроверкой.

### Шаблон «Карта ЛР N» (в `progress.md`)

```markdown
## Карта ЛР N
Источники: <файл + страницы / слайды / ячейки>
Требования:
- [ ] <требование> — <источник, стр.>
Критерии приёмки:
- [ ] <критерий> — <источник>
Делает студент руками: (нет — так и написать)
- [ ] <что построить/сделать> — <инструмент> — скриншот в `solution/labN/img/<имя>.png`
Отчёт: нет | `solution/labN/report.docx`, шаблон <файл>, структура <источник>
Проверка запуском: <команда из «Окружение»> | не запускается (почему)
Вне курса (общие знания с пометкой): <тема — почему в материалах нет>
```

### Ручные шаги (GUI-инструменты)

Visual Paradigm, ELMA 365, Rational Rose, редактор IDEF1X и т.п. агент не запускает. Агент делает:
- черновик диаграммы в PlantUML / Mermaid в нотации курса (`solution/labN/draft/`) — источник для переноса, не результат;
- пошаговую инструкцию переноса в инструмент (по методичке, со ссылкой на страницы);
- список скриншотов с именами файлов.

Студент строит в инструменте, сохраняет скриншоты в `solution/labN/img/`, говорит агенту — агент отмечает пункт в Карте. Нет скриншота — пункт не отмечен.

## Окружение

Команда «проверки запуском» для каждой ЛР — из этого раздела; скептик выполняет её сам.

- **Python** (ProgPractice, NLP, проверка выкладок): venv **вне OneDrive** — `%USERPROFILE%\.venvs\studies2026-<scope>` (тысячи файлов venv в OneDrive тормозят синхронизацию). Список пакетов — `<Предмет>/solution/requirements.txt` (в Git). Создать: `python -m venv "$USERPROFILE/.venvs/studies2026-<scope>" && "$USERPROFILE/.venvs/studies2026-<scope>/Scripts/python" -m pip install -r <Предмет>/solution/requirements.txt`.
- **Ноутбук** — выполнить сверху вниз в чистом ядре, результат не в папку решения:
  `"$USERPROFILE/.venvs/studies2026-progpractice/Scripts/python" -m jupyter nbconvert --to notebook --execute <ноутбук> --output-dir "$TMP/nbcheck"`.
- **SQL** (DBMS; пособие — PostgreSQL 15): Docker Desktop должен быть запущен. Контейнер: `docker run -d --name dbms-pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 postgres:15` (дальше `docker start dbms-pg`). Прогон: `docker exec -i dbms-pg psql -U postgres -v ON_ERROR_STOP=1 < solution/labN/<файл>.sql`. Демон не запущен — сказать пользователю, не выдавать вердикт «проверено».
- **Web** (WebDev): Node.js; `npm ci && npm run build` (+ `npm test`, если есть) в папке ЛР.
- **Выкладки** (DiffEq, MathSec): решение в Markdown с LaTeX (`$...$`) — `solution/labN/solution.md`; проверка ответов `sympy` там, где это возможно (скрипт `check.py` рядом). Как сдаётся (рукописно / печать) — уточнить у пользователя, записать в `task.md`.

## Отчёт

Если ЛР сдаётся документом (SE: ЛР 3, BPMN, РГР; DBMS: «составить отчёт» в каждой ЛР пособия):
- файл `solution/labN/report.docx`; структура — по шаблону/примеру из `materials/` (правило 6), титул — группа ФИТ-242 (в шаблонах SE стоит ФИТ-241 — заменить);
- собирается скиллом `anthropic-skills:docx` или вручную студентом — выбрать с пользователем при первой ЛР предмета, записать в `progress.md`;
- картинки — из `solution/labN/img/`;
- проверка: текст — `python .claude/scripts/docx2txt.py solution/labN/report.docx`, сверка с Картой.
- Требований к оформлению нет в материалах — не выдумывать, вписать в «Открытые вопросы».

## Стиль текстов

Ответы в чате могут быть сжатыми (плагин caveman и т.п.), но `log.md`, `progress.md`, `task.md`, `INDEX.md`, отчёты и markdown-ячейки решений пишутся **полным литературным русским** — их читает преподаватель и сам студент через месяц.

Учёт ведётся только в `task.md` / `progress.md` / `log.md`. Пользовательские скиллы `memory-bank` и `task` (`.memory-bank/`, TDD) в этом репозитории не использовать.

## Материалы

Материалы = то, по чему проверяют. Решение, верное «вообще», но не по методичке, не сдаётся.

### Где что лежит

```
<Предмет>/materials/
├── INDEX.md    # оглавление: файлы, сроки, критерии, карта по ЛР, страницы пособий — читать ПЕРВЫМ
├── notes/      # полный текст каждого PDF/DOCX (маркеры <!-- стр. N -->) — искать Grep, не читать целиком
└── ...         # оригиналы
```

### Правила

1. **Порядок доверия:** задание ЛР (`task.md`, методичка ЛР) → методика рейтингового контроля → шаблон → пример → лекции/ноутбуки с пар → пособие → общие знания. Противоречие между источниками — не выбирать самому, спросить пользователя.
2. **Карта перед стартом ЛР.** Перед первой строкой решения: прочитать `materials/INDEX.md`, по нему — нужные куски `notes/`. Записать в `progress.md` блок «Карта ЛР N»: файлы + страницы, требования, критерии. Дальше работать по карте, методички заново не перечитывать.
3. **Читать выжимки, не оригиналы.** Текст искать в `notes/` через Grep по ключевым словам / номеру страницы. Оригинал (PDF/DOCX) открывать только ради картинок, схем, таблиц, потерянных при извлечении.
4. **Критерии → чек-лист.** Требования методички и критерии приёмки переносить чекбоксами в «Карту ЛР N». Статус `готова` — только когда отмечены все.
5. **Методы как на парах.** Библиотеки, подходы, термины — из лекций и ноутбуков преподавателя (раздел в `INDEX.md`). Два случая:
   - в материалах **есть** способ, а берём другой — выход за курс: пометка в решении + причина в `log.md`, на защите спросят;
   - в материалах темы **нет** (таблицы и CSS в WebDev, `CREATE INDEX` / полнотекстовый поиск в DBMS) — общие знания допустимы (последняя ступень порядка доверия), с пометкой «в материалах нет, источник: <документация>». Это не выход за курс; записать в строку «Вне курса» Карты.
   Сторонние скиллы (`.claude/skills/`) — тоже «общие знания»: их нотации и методики (C4, ADR, ISO 25010 и т.п.) не подменяют методичку.
6. **Оформление по шаблону.** Титульный лист своей группы (ФИТ), структура отчёта — по шаблону/примеру. Из примеров брать структуру и объём, текст не копировать.
7. **Ссылка на источник.** В решении/отчёте у требования или метода — откуда он: «пособие PostgreSQL, с. 61», «Лекция 2, слайд 12».
8. **Не выдумывать.** Нет в материалах (задания ЛР, варианта, срока) — так и сказать, вписать в «Открытые вопросы» `progress.md`. Не достраивать задание по аналогии.
9. **Архив — не задание.** `materials/archive_*` — только справка.
10. **Новый материал — сразу в учёт** (`/add-material <Предмет> <файл>`). Положили файл → извлечь текст в `notes/` → строка в `INDEX.md` (+ сроки/критерии, если есть) → запись в `log.md` → коммит `docs(<scope>): add <что>`.

Извлечение текста: PDF — `pypdf` (по странице, маркер `<!-- стр. N -->`), DOCX — `python .claude/scripts/docx2txt.py <файл> <выход.md>`, DOC — `antiword -m UTF-8.txt`.

## Git

Репозиторий: https://github.com/mm-shkurin/studies_2026 (публичный). Методология — упрощённый GitHub Flow из absolute555/textery: без PR, коммиты прямо в рабочую ветку.

### Ветки

| Ветка | Роль |
|---|---|
| `main` | Снимок `dev` на момент последней сдачи любой ЛР. Там может быть незаконченная работа других предметов — «что сдано» показывают теги, не `main`. Прямых коммитов нет — только fast-forward из `dev`. |
| `dev` | Рабочая ветка. Все коммиты сюда. |

- Сдали ЛР (статус `сдана` в `progress.md`, коммит с записью в журнал сделан) → тег на этот коммит и снимок в `main`:
  `git tag -a <scope>-lab<N>-submitted -m "<Предмет> ЛР N сдана" && git push origin <scope>-lab<N>-submitted && git checkout main && git merge --ff-only dev && git push && git checkout dev`.
  Пример тега: `progpractice-lab1-submitted`. Защитили — второй тег `<scope>-lab<N>-defended`.
- Отдельные ветки на ЛР не заводить: работа одна, ветка одна.
- Репозиторий лежит в OneDrive — принятый риск (решение пользователя 2026-09-27). Ошибка `index.lock` / «файл занят» — сначала проверить, не синхронизирует ли OneDrive `.git/`, не удалять lock вслепую. venv и `node_modules` — вне OneDrive или в `.gitignore`.

### 1 запись в журнал = 1 коммит

Значимое действие (см. «Правило записи») завершается **одним коммитом**, в котором лежат вместе:
- изменения работы (решение, задание, материалы);
- новая запись в `log.md`;
- обновлённый `progress.md`.

Порядок: сделать работу → записать `log.md` + `progress.md` → `git add` конкретных путей → коммит → push в `dev` → ответ пользователю.

Мелочи без записи в журнал (опечатка, форматирование) — отдельный коммит `style:`/`docs:` без записи в `log.md`.

### Сообщение коммита

Conventional Commits, английский, повелительное наклонение, до ~72 символов, без точки:

```
<type>(<scope>): <what>

<why — если неочевидно>
```

- `scope` — папка предмета в нижнем регистре (`progpractice`, `webdev`, `se`, `dbms`, `diffeq`, `mathsec`, `nlp`, `ooad`) или `repo` для общего.
- `type`: `feat` — решение/часть ЛР; `fix` — исправление решения; `docs` — задания, материалы, README, журнал без работы; `chore` — структура, конфиги, скиллы; `refactor`, `test`, `style` — как обычно.
- Subject повторяет заголовок записи в `log.md` (по-английски): `feat(progpractice): lab 1 load data and split train/test`.

### Запрещено без явной просьбы

- `git reset --hard`, `git checkout -- .`, `git restore .`, `git clean -fd`, `git push --force` — сначала `git status --short`, закоммитить или спросить.
- `git add -A` / `git add .` вслепую — смотреть `git status`, добавлять пути.
- Коммитить `.claude/settings.local.json`, `.venv/`, секреты, токены.

## Прочее

- Язык общения и документов — русский. Код, коммиты, имена новых файлов решений — латиница.
- Студент должен уметь объяснить каждое действие на защите: решения фиксировать в `log.md` с причиной.
- Персональные данные одногруппников (рейтинги, ФИО) в репозиторий не сохранять — только ссылки.
