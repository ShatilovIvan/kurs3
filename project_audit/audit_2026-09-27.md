## 3. Находки

Уровень: **HIGH** — сломает цикл ЛР или приведёт к потере баллов; **MED** — будет мешать; **LOW** — улучшение.

### HIGH

1. **Скептик не может проверить то, что обязан проверить.** В `lab-skeptic.md` (режим `solution`, пункт B) сказано «notebook top-to-bottom in a clean kernel / script / SQL», но на машине нет `jupyter` / `nbconvert` и `psql`. Без этого `сдавать` по ProgPractice и DBMS будет выдан на непроверенном решении или не будет выдан никогда.
   *Исправить:* правило окружения в `CLAUDE.md`: `<Предмет>/solution/.venv` + `requirements.txt`, в ProgPractice добавить `jupyter nbconvert` (`jupyter nbconvert --to notebook --execute`); для DBMS — `docker run postgres` и команда проверки в Карте ЛР.

2. **В цикле ЛР нет отчёта.** DBMS («составить отчёт» в каждой ЛР пособия) и SE (ЛР 3 — «отчёт MS Word с описанием и скриншотами», РГР) сдаются документами. Правило 6 («оформление по шаблону») есть, но нет шага цикла, формата файла и проверки у скептика: пункт D ищет «template/title page», но не знает, как открыть `.docx`.
   *Исправить:* шаг «Отчёт» между «Решение» и `/check-lab solution`: `solution/labN/report.docx` по шаблону и титулу ФИТ-242; скептик извлекает текст `.docx` тем же способом, что и материалы (`word/document.xml`).

3. **ЛР в GUI-инструментах не описаны.** Visual Paradigm (SE ЛР 3), ELMA 365 (BPMN), IDEF1X-редактор (DBMS ЛР 1), Rational Rose (UML-пособия). Агент не может строить в них диаграммы и делать скриншоты, а в `progress.md` нет способа пометить шаг как ручной. Итог — ЛР будет висеть в `в работе` без понятного следующего шага.
   *Исправить:* в Карте ЛР отдельный список «Делает студент руками» (что построить, в каком инструменте, куда положить скриншоты: `solution/labN/img/`). Агент готовит черновик (PlantUML/Mermaid + текст шагов), студент переносит в инструмент.

### MED

4. **Скиллы не совпадают с курсами, README это скрывает.** `enterprise-architecture` в своём описании прямо пишет: «Do NOT trigger for … database or ER schema design, code-level UML or sequence diagrams» — ровно то, что нужно в SE (прецеденты, последовательности, классы) и DBMS (ER). README же пишет «SE, OOAD». `mvp-scope-cutting`, `estimation-from-requirements`, `stakeholder-interview-guide`, `requirements-gap-analysis` в ЛР этих курсов не нужны. Кроме того, эти скиллы подтягивают TOGAF, RICE, ISO 25010 — это выход за курс, который правило 5 требует обосновывать на защите.
   *Реально полезны:* `non-functional-requirements-elicitation` (SE, РГР, раздел 1 — «не забыть нефункциональные требования»), `ambiguity-detection-in-requirements` (разбор размытых заданий, например нумерации ЛР в SE), `modern-web-app-architecture` частично (WebDev ЛР 2–3).
   *Исправить:* удалить 4–5 нерелевантных скиллов или хотя бы исправить колонку «Где пригодится» в README, чтобы агент не выбирал их по README.

5. **Агенты без frontmatter.** `.claude/agents/debugger.md` и `lab-skeptic.md` начинаются с `# Agent: …` без `---name/description/tools---`. Как субагенты Claude Code они не регистрируются; скиллы обходят это, запуская `general-purpose` с просьбой прочитать файл. Следствие: у скептика есть Edit и Write, и «read-only» держится только на тексте промпта.
   *Исправить:* добавить frontmatter (`name`, `description`, для скептика `tools: Read, Grep, Glob, Bash`) и вызывать по `subagent_type: lab-skeptic`.

6. **Повторяющиеся процедуры описаны только текстом.** «Построить Карту ЛР N» (правило 2) и «добавить новый материал» (правило 10: извлечь текст → INDEX → log → коммит) будут выполняться десятки раз, но живут в прозе `CLAUDE.md`. После `/clear` агент будет выполнять их каждый раз немного по-разному.
   *Исправить:* скиллы `/start-lab <Предмет> N` (Карта → `/check-lab plan`) и `/add-material <Предмет> <файл>`.

7. **Правило записи не проверяется автоматически.** «Проверка перед ответом» (изменён `solution/`, а `log.md` не тронут) выполняется, только если агент о ней вспомнит.
   *Исправить:* Stop-хук в `.claude/settings.json`: `git status --porcelain` — если есть изменения в `*/solution/`, но не в соседнем `log.md`, выдать предупреждение.

8. **Правило merge в `main` противоречит одной ветке на 8 предметов.** «Сдали ЛР → `merge --ff-only dev` в `main`» переносит в `main` и всю незаконченную работу других предметов. Тогда фраза «`main` = сданные ЛР» перестаёт быть правдой.
   *Исправить:* либо честно назвать `main` «снимок на момент последней сдачи», либо отказаться от `main` и ставить тег `progpractice-lab1-submitted` на коммит сдачи — это проще и точнее.

9. **Публичный репозиторий.** В корневом `log.md` лежит личный e-mail. В `ProgPractice/task.md` — ссылка на таблицу рейтинга группы: правило «только ссылки» соблюдено, но если таблица открыта по ссылке, данные одногруппников фактически публикуются. Методички преподавателей тоже публичны (это решение пользователя, записано в журнале).
   *Исправить:* убрать e-mail из `log.md`; рассмотреть приватный репозиторий — это закрывает все три вопроса сразу.

10. **Git внутри OneDrive.** Синхронизация OneDrive и `.git/` конфликтуют: блокировки файлов, «файлы по запросу», дубликаты `index-DESKTOP.lock`. Раз есть GitHub, двойная синхронизация не нужна.
    *Исправить:* перенести репозиторий из `Desktop` (OneDrive) в папку вне синхронизации, например `C:\dev\studies_2026`.

- **«1 запись = 1 коммит»**: история Git и журнал рассказывают одно и то же.
- **Решения с причинами в `log.md`** — прямая подготовка к защите.
